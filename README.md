# 实时同声传译 · 中文 ⇄ 英 / 日 / 德 / 法 / 西 / 葡 / 韩 / 泰 · 粤语 / 上海话 → 普通话

面对面会谈用的实时传译工具。你说中文，对方立刻看到译文字幕（多数语言对还能听到译音）；
对方说外语，你立刻看到中文字幕并听到中文语音。

**语言对**（顶栏切换）

| | 双向？ | 有译音？ | 上游会话数 |
|---|---|---|---|
| **中英自动** | ✅ | ✅ | 1 条 |
| **中日自动** | ✅ | ✅ | 2 条 |
| **中德自动** | ✅ | ✅ | 2 条 |
| **中法自动** | ✅ | ✅ | 2 条 |
| **中西自动** | ✅ | ✅ | 2 条 |
| **中葡自动** | ✅ | ✅ | 2 条 |
| **中韩自动** | ✅ | ❌ 仅字幕 | 2 条 |
| **中泰自动** | ✅ | ❌ 仅字幕 | 2 条 |
| **粤→普** | ❌ 单向 | ❌ 仅字幕 | 1 条 |
| **沪→普** | ❌ 单向 | ❌ 仅字幕 | 1 条 |

会话数为什么不一样：火山只提供了 `zhen` 一个"中英反转互译"值，一条会话就能包办
双向，还能处理一句话里中英混杂。其余语言对没有对应的反转值，只能开 zh→X 和 X→zh
两条，同一路音频喂给两条、再靠方向闸门放行其一，**费用约为中英的两倍**。

韩语和泰语为什么没有译音：火山 s2s 只支持 8 个语种（zh / en / ja / de / fr / es / pt / id），
韩泰只在 s2t 的 20 语种里。实测 `zh2ko-s2s` / `zh2th-s2s` 模型确实不存在。

两个方言（粤语 `yue-CN`、上海话 `sh-CN`）情况完全一样：s2s 模型不存在
（`volc_tob-yue-CN2zh-s2s` / `volc_tob-sh-CN2zh-s2s` 都报 not found），
反向 `zh→方言` 也不存在，只有 s2t 的「方言 → 普通话」可用。

**闽南语做不了**：火山只提供粤语和上海话两种方言。
`nan-CN` / `nan` / `minnan` / `hokkien` / `zh-nan` / `nan-TW` / `mn-CN` /
`hokkien-CN` 八个候选代号全部被拒（`InvalidData:sp for model:default`）。
上海话是可用的，需要的话可以照粤→普的方式加一个沪→普。

**后端**（设置面板切换）

| | 模型 | 特点 |
|---|---|---|
| **火山引擎**（默认） | 同声传译 AST 2.0 | 国内直连、支付宝充值、支持术语库、支持中日 |
| **OpenAI** | `gpt-realtime-translate` | 自动识别语种，需代理与境外信用卡，**只支持中英、不支持术语库** |

**核心能力**

- **十个语言对** —— 中文与英 / 日 / 德 / 法 / 西 / 葡 / 韩 / 泰 互译，
  外加粤语、上海话转普通话
- **语音进、语音出** —— 字幕和译音同时给到，用的是专门为口译训练的同传模型，
  不是"识别 + 翻译 + 合成"拼装的
- **方向全自动** —— 不用手动切换谁在说话；中文里夹外文术语（"这个 pipeline 的 latency"）
  也不会把方向判反
- **术语库** —— 最多 10 条专有名词，让模型把音听对，**译音也跟着念对**
- **自动归档** —— 每句定稿即落盘，一天一个 JSONL，页内可查看 / 导出 / 删除
- **防回环** —— 同一房间外放扬声器不会啸叫，也不会自我循环翻译
- **译音追赶** —— 自动补偿合成语音比原话长导致的累积延迟
- **演示模式** —— 不用任何 Key 就能把整套界面走一遍

## 归档与导出

**屏幕上最多保留 2000 句**（约 3 小时连续对话），超出后最早的会从 DOM 摘掉并给一次提示。
但内容不会丢——每句定稿后都会立刻追加到归档文件：

```
transcripts/2026-08-07.jsonl
```

一天一个文件，同一天的多场会谈都追加进去，用 `session` 记录分隔。
**刷新页面会自动把当天已归档的最近 500 句铺回来**，接着往下记。

### 文件管理

点顶栏「**记录**」打开：列出全部归档，每份显示**句数 · 会谈场次 · 大小 · 时间范围**，
当天那份标「今天」。每份有四个操作：

| | 说明 |
|---|---|
| **查看** | 在页面里直接翻，不用下载 |
| **Markdown** | 按会谈分段、带时间戳，适合发给别人 |
| **JSONL** | 原始归档，适合自己后续处理 |
| **删除** | 二次确认，不可撤销；删今天的会额外提示"正在进行的会谈仍会继续写入" |

删除只认 HTTP `DELETE` 方法，避免被浏览器预取之类的操作误触发。

Markdown 导出长这样，按会谈分段、带时间戳：

```markdown
## 会谈 13:08:08

> 火山 AST 2.0 · 中 ⇄ 日本語

**13:08:10**　こんにちは。

> 大家好。
```

### 为什么是 JSONL 而不是数据库

append-only 天生抗崩溃（进程被杀也不会损坏已写内容），能直接 `grep`，
导出就是读文件。这个场景不需要跨会谈检索，上数据库是徒增复杂度。

同理也没做"页面只留 50 行 + 滑动时分页拉取"：每行约 5 个 DOM 节点，
2000 行浏览器毫无压力，而双向无限滚动的滚动锚定、重复拉取、贴底状态丢失
这些坑在会谈现场很显眼。用最复杂的方案去解一个不存在的性能问题不划算。

> 如果以后确实想要跨会谈检索，Node 22 内置了 `node:sqlite`（无需依赖），
> 换成 SQLite 的成本不高。

## 术语库

产品名、公司名最容易被听错。实测 `SensePedia` 会被识别成 `SensePDU` 或
`SenseTimeedia`（模型往已知的 SenseTime 上靠）。

设置面板里可填最多 **10 条**术语：

| 正确写法 | 常见误识（可选） |
|---|---|
| `SensePedia` | `SensePDU、SenseTimeedia` |

生效方式分两段，**这是实测出来的分工**：

1. **`hot_words_list`（火山侧）** —— 引导模型把音听对。
   实测 `SensePDU` → `Sense pedia`，音已经对了，**所以译音也念对了**。
2. **本地文字纠正** —— 把写法规范化成 `SensePedia`。

大小写和空格**自动收编**：填 `SensePedia` 就能同时改掉 `Sense pedia` /
`SENSE PEDIA`。只有发音层面的误识才需要手工填第二栏。词边界有保护，
`sensible pediatrics` 这类无关词不会被误伤。

## 三个已知特性，会谈前请知悉

### 1. 首句译音约 2 秒才出来

实测火山首包延迟 **2.2–2.5 秒**。这不是卡顿——同传模型会**故意等足上下文**再开口，
否则会译出半截错句。字幕原文出现得更早（几百毫秒）。

### 2. 译音略长于原话，程序会自动追赶

合成语音时长约为源语音的 **1.2 倍**。差值不大但会累积，所以做了两级补偿：

- 积压 > 1.5s 起逐级加快播放（最高 1.35 倍）
- 积压 > 8s 直接跳过重排

顶栏会显示「译音滞后 X.Xs」，超过 4 秒变黄。**持续变黄就在句子间多留停顿。**

### 3. 回声/啸叫

同一房间外放时，扬声器的译音会被麦克风重新拾取。两个后端的防护强度不同：

- **OpenAI** 是双会话，有「播放期间冻结方向」这层保护 → 用「仅回声消除」即可
- **火山中英** 是 `zhen` 单会话双向，**没有这层保护** → 默认用「播放译音时压低麦克风」

万一还是循环，按顺序调整：

1. **把扬声器音量降到 60–70%** —— 最有效，先试这个
2. 回声处理改成「**播放译音时静音麦克风**」（绝不啸叫，代价是译音播放时对方插话会丢）
3. 终极方案：双方各配一副耳机，回环从物理上消失

## 结构

```
server.js                静态服务 + WebSocket 会话 + 配置/自检 API
backends/
  common.js              语种检测 · 方向路由 · 分句成行 · 术语库编译（后端共用）
  volcengine.js          火山 AST 2.0，裸 protobuf over WebSocket，多会话
  openai.js              OpenAI 双会话 + 方向闸门
  mock.js                演示后端，不需要 Key
protos/                  火山官方 .proto（运行时由 protobufjs 加载）
public/                  前端：纯展示层
```

**方向路由、分句、术语纠正全在服务端**，前端只负责渲染，所以两个后端、
两个语言对对前端呈现的是同一套事件：

```
{ t:'ready', backend, pair, noAudio, inputRate }
{ t:'dir',   dir }                        方向变化，形如 zh2en / ja2zh
{ t:'line',  id, dir, src, dst, final }   一整句的最新全量状态
{ t:'audio', pcm }                        译音，base64 PCM16 24kHz
{ t:'usage' | 'error' | 'closed', ... }
```

语言对是**建连参数**（`/ws?pair=zhja`），切换必须重连——不同语言对的上游会话数和模式（s2s / s2t）都不一样。

### 语言对表是唯一真源

加一个语种只需要往 `backends/common.js` 的 `PAIRS` 里加一行，别处都从它推导：

| 由 `PAIRS` 推导出来的东西 | 位置 |
|---|---|
| 开几条上游会话、每条的源/目标语种、走 s2s 还是 s2t | `volcengine.js` 的 `planSessions()` |
| 方向判别认哪两种语种 | `common.js` 的 `detectPairLang()` |
| 左右两栏的表头 | 前端 `headLeft` / `headRight` |
| 空状态里的语种清单、哪些是"仅字幕" | 前端 `renderHints()` |

最后一条是补的教训：那段提示文案原先写死在 HTML 里，加了德法西葡之后仍写着
"对方说英文/日语"，**连着漏了两回**。改成由数据生成后就不会再脱节了。

字段含义：

- `a` / `b` —— `a` 排左栏、`b` 排右栏，方向标识形如 `a2b`
- `left` / `right` —— 两栏的表头文字
- `srcCode` —— 方言专用，上游要的语种代号（`yue-CN` / `sh-CN`），与用作短名的 `a` 不同
- `oneWay` —— 单向，方向定死不做判别
- `noAudio` —— 只能走 s2t，没有译音

## 踩坑记录

这些都是文档没写、或者写了但与实际不符的，实测确认后记在这里。

### 火山 AST

**帧格式**：WebSocket 消息体是**裸 protobuf**，没有老 ASR/TTS 那套四字节帧头。
文档正文没写，只能从附件 `protos.tar.gz` 和 `ast_python_client` 里看出来。

**译音是 float32 不是 int16**：文档在 `target_audio.rate` 的备注里藏了一句
"pcm 格式：16000Hz 下默认 16 位整型，**24000Hz 下默认 32 位浮点型**"。
按 int16 解读的话是一片噪声，且时长虚报一倍。代码里既显式声明了 `bits`，
接收端也做了 float32 自动识别兜底（float32 语音样本必落在 `[-1,1]`，
int16 数据按 float32 解读则指数位随机、绝大多数会变成 1e30 量级）。

**`correct_words` 是死字段**：参数表里写了替换词功能，但官方 proto 的 `Corpus`
消息里**没有这个字段**，protobuf 编码时被静默丢弃。文字纠正只能自己做。

**字幕增量语义**：`651`/`654` 是**增量片段**，`652`/`655` 是**整句全量**。

**计费字段是 PascalCase**：`BillingItem` 里是 `Unit` / `Quantity`，不是小写。

**ASR 不强制按声明的源语种识别**：中日双会话时，喂中文音频，两条会话都如实
转写出中文，其中 ja→zh 那条因为源语种==目标语种而原样透传。
这反而给出了干净的方向判据 —— 只看 ja→zh 那条的原文有没有假名。

**中日只能走声音复刻模式**：s2s 指定音色模式要求"目标语种必须为中英"，
传了 `speaker_id` 就输出不了日语。

**粤语的 s2s 模型压根不存在**：文档说粤语"仅支持作为源语种"，但实测比这更严格 ——
`StartSession` 会正常返回 150，一送音频才报
`InvalidData:group model:volc_tob-yue-CN2zh-s2s not found`，
反向 `zh2yue-CN` 同样不存在。**只有 s2t 的 `yue-CN→zh` 可用**，
所以粤普只能出字幕、且做不了反向。踩这个坑要靠实际送音频，光看握手结果会被骗。

**拿不到账户余额**：`UsageResponse` 只回本次消耗，余额要走另一套需 AK/SK
签名的 OpenAPI。所以界面显示的是"已用"而非"剩余"。余额请到
[控制台的同声传译体验页](https://console.volcengine.com/speech/new/experience/translate?projectName=default)
查看。

### 方向判定

必须按**整句累计文本**判，不能按单个增量片段判。"这是我们 SensePedia 的产品
经理"里的 `SensePedia` 片段不含汉字，单看它会把整句方向翻成英译中。

语种判别按**文字系统**而非语种：德语和法语都是拉丁字母，从字面分不出语种，
但"用的哪套书写系统"是确定的，再结合当前语言对只有两种可能语种就能唯一定位。

判别顺序是 **谚文 → 泰文 → 假名 → 汉字 → 拉丁字母**：韩语可能夹汉字、日语必然
夹汉字，先匹配汉字会把它们都误判成中文。汉字排在拉丁字母前，是因为中文夹外文
术语是常态，而外语母语者的转写里不会冒出汉字。

**译文比原文晚 2 秒以上到达**，所以译文不能靠"第 N 句原文配第 N 句译文"的独立
计数来配对 —— 中间一旦穿插超时归档，两个计数就错开一格，表现为上一行只有原文、
下一行只有译文。改成译文按顺序认领最早那条"有原文、还没译文"的行，与时序无关。
同理，空闲归档超时必须大于译文滞后（现为 5 秒），否则每句都会在译文到达前被提前归档。

### OpenAI

**握手成功不代表 Key 有效**：Key 无效时上游会先回 `101`，再推一条 error 事件
并以 close code `3000` 断开。自检必须等这条消息。

**不支持术语库**：官方文档明确 "No custom prompting or glossaries"。

## 其他

- Key 保存在 `config.json`（权限 600，已 gitignore）。也支持环境变量
  `VOLC_API_KEY` / `OPENAI_API_KEY`。
- 归档在 `transcripts/`（权限 600，已 gitignore）。演示模式不写归档。
- 接口里的 `date` 参数会拼进文件路径，服务端用 `^\d{4}-\d{2}-\d{2}$` 卡格式
  并复核最终路径落在归档目录内，防止 `?date=../../etc/passwd` 这类穿越。
- 服务只监听 `127.0.0.1`，局域网访问不到。
- 换端口：`PORT=8080 npm start`
- 调试火山上游事件流：`DEBUG_VOLC=1 npm start`
